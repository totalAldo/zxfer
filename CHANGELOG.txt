2026.09.28
-CI: retire the `posh` unit lane and fix the kcov coverage job; both were non-blocking and had been failing for months, so every run carried a red annotation. `posh` is not supported (`docs/platforms.md` says why): its `case` patterns have no POSIX character classes, which zxfer's checks use; it has no `printf` or `kill` builtin, and procps-ng 4.0.4's `/usr/bin/kill` inverts the status of zxfer's process-group probe; and it cannot parse a quote in a comment or a `case` pattern without a leading `(` inside `$(...)`, which eight test files contain. The lane last passed on 2026-04-09 and failed 20 of 31 suites on 2026-09-28; dash, `bash --posix`, BusyBox ash, macOS, FreeBSD and OmniOS lanes are unchanged. The devcontainer and `tests/validate.sh doctor` drop `posh` too. The kcov job ran the suites in the Debian-slim `kcov/kcov` image, which has no `ps` (zxfer requires it at startup) and no `ssh` (the remote backup cases resolve it), so most suites failed there; the job now builds the pinned image with `procps` and `openssh-client` added. A cleanup-wrapper unit test that checked its output for the substring `702` failed whenever the test shell's PID contained it (seen once in the kcov container); it now compares the whole line. `src/` is unchanged.
-Fix `-V` elapsed times with BusyBox `date`, which prints `%3N` as nanoseconds without zero padding: two clock readings could differ in length, so the `-V` summary could print a large negative `elapsed_seconds` and a stage timer a wrong duration. A reading now takes the millisecond field only when it is the seconds field followed by exactly three digits, as GNU `date` prints it, and otherwise uses whole seconds, as on BSD and illumos. The summary never prints a negative elapsed time (a clock that went backwards reports 0). Found by the `-V` contract test on the BusyBox unit lane; `tests/test_zxfer_profile.sh` pins BusyBox-style, nanosecond and mismatched readings and the non-negative summary.

-`ZXFER_ERROR_LOG` mirroring takes no lock. Each failure report is appended with one `O_APPEND` write after the path checks, which are unchanged (absolute path, no symlinked component, a parent owned by root or the effective user that other users cannot write unless it is sticky, and a regular 0600 log owned by root or the effective user) except for one new refusal: a log with more than one hard link (`... because it has N hard links`, or `... because its link count could not be determined`), which keeps a report out of a root-owned 0600 file that another user hard-linked into a shared parent. A missing log is created under umask 077 with noclobber, and set to mode 0600 (a default ACL can override the umask) only after it passes the other checks: noclobber still opens a FIFO or a device, even through a symlink, that another user puts at the name just before the open, and chmod follows symlinks. The owned lock directory (pid plus `ps` start token, stale-owner reaping, checked release), the fallback lock under the temp directory and the staged copy and rename of the whole log for each report are gone with `src/zxfer_error_log.sh`; the path checks and the append now live in `src/zxfer_reporting.sh`. awk writes the report, not the shell's `printf`: bash, which is `/bin/sh` on macOS and many Linux systems, line-buffers its builtins' output, so a report printed by the shell goes out one line per write: with a `printf` writer, four concurrent failing runs interleaved their reports in 11 of 12 tries, and with awk in none. A failing run with the log set now costs 130 ms instead of 386 ms under bash 3.2 and 88 ms instead of 303 ms under dash (macOS, usage failure, mean of 20 runs; 80 ms and 55 ms without the log, unchanged). This also fixes mirroring on hosts whose `ps` cannot report zxfer's own start time: each failure spent about 2.5 s retrying the lock, then dropped the report with "unable to acquire ZXFER_ERROR_LOG lock" (reproduced with a `ps` that prints nothing; BusyBox `ps` rejects the `-p` the start token needs). Compatibility: the warnings "unable to acquire ZXFER_ERROR_LOG lock", "unable to release ZXFER_ERROR_LOG lock ... (status N)", "unable to create ZXFER_ERROR_LOG staging directory" and "unable to chmod ZXFER_ERROR_LOG file ... to 0600" no longer occur; no `.zxfer-error-log.lock.*` directory beside the log, `.zxfer-error-log.lock.d` tree under the temp directory, or staging directory beside the log is created (leftovers from earlier versions can be deleted once no older zxfer runs); and a hard-linked log is refused instead of replaced by a one-link copy. Given up, as `SECURITY.md` now states: the validated file is no longer pinned while it is written, so root or the effective user can swap the path between the checks and the write, reports from concurrent runs can interleave on NFS or when one report needs more than one write (larger than the file system block size, often 4 KiB), and in a shared sticky parent another user who puts a FIFO at the name just as zxfer creates the log holds the failing run's exit until the FIFO is opened. `KNOWN_ISSUES.md` drops the GNU `stat` setgid entry, which affected only the lock directory. Tests: `tests/test_zxfer_error_log.sh` becomes the reporting fragment `tests/suites/zxfer_reporting_error_log_tests.sh`; its 59 lock-protocol, fallback-lock, staging and deleted-step tests go, 17 path and append tests stay, and 8 new tests pin the hard-link refusal, an unreadable link count, a log that cannot be created, a new log narrowed to 0600, a symlink or hard link at a new log's name whose target keeps its mode, a FIFO at the log path refused without an open, a 300 KB report (awk reads the report from a pipe, since an environment string is capped at 128 KiB on Linux), and four concurrent failing runs that must each leave one intact report. -Security fix: `-v`/`-V` printed property values raw. Exploiting it needed only the `userprop` permission on the source and an operator running `-v` or `-V`. C1 control characters and the `-U` unsupported-property warning are not escaped yet (`KNOWN_ISSUES.md`, Low).

-Security fix: `-P`/`-o` property reads guessed where a multi-line `zfs get -H` value ended, and zfs prints values raw. A user property value shaped like another record (for example `x<TAB>local<LF>hn:fake<TAB>y`) was cut at the fake record: the destination got the truncated value, and with `-N` (or `-R` when the continuation carried the dataset name) the run also set the injected user property (`hn:fake=y`), then exited 0. Anyone allowed to set user properties on the source (for example through `zfs allow userprop`) could change the replica's user properties. A continuation shaped like a native property was refused only because zfs rejects a property given twice. Affected: every earlier release, since none read the property names separately; upstream zxfer (`upstream-compat-final`) joins the `zfs get -H` output with `tr`, so any value holding a tab or line feed is misread there. Every `zfs get all` read, source and destination, local and over `-O`/`-T`, now reads the machine and human values and then lists the property names alone (`zfs get -H -o property all`, or `-r -t filesystem,volume -H -o name,property all` for the recursive prefetch). A value line is used only in an unbroken run from the first line: line i must start with the i-th listed name, the next line with the next name, and no other line may start with either name. Every property after that run is read alone (`zfs get -H[p]o property,value,source -- PROP DS`) and split at its last TAB; the recursive prefetch leaves such datasets to per-dataset reads. A property list that is malformed or repeats a name, or a lone read that does not return that property, fails the run with `Failed to parse the properties of dataset [DS]: ...` or `Failed to read property [P] of dataset [DS]: ...`. One narrow race remains: a dataset destroyed and recreated (or renamed away and back) between the value reads and the name list of a recursive read can take values forged by the value printed before it, native properties included (`KNOWN_ISSUES.md`, Low).
-Fix property reads of user properties whose names start with `-` (OpenZFS accepts names such as `-x:y`; only a colon is required). A `-P` or `-o` run (with `-N` or `-R`) therefore stopped with `Failed to read property [-x:m] of dataset [DS]: invalid option 'x' ...` (exit 2) at the first dataset, source or destination, holding such a property with a multi-line value or after one; a recursive run left the later datasets unreconciled and unsent.
